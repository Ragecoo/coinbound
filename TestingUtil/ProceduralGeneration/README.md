# Процедурная генерация подземелий

Консольное приложение на C# / .NET 10 без внешних пакетов. Карта отображается
**цветными символами**. Видно весь процесс: строительство комнат, прокладку
лабиринта, соединение открытых проходов, обходные пути и выход в конце тупика.
Над картой расположен зелёный **прогрессбар 0–100%**, а прямо под ним меняются
подписи: «Возведение стен подземелья...», «Создание прямоугольных залов...»,
«Размещение входа и фонтана...», «Прокладывание коридоров лабиринта...»,
«Создание обходных путей...», «Поиск выхода в дальнем тупике...».
После завершения выводится вторая карта: её цвета обозначают варианты спрайтов.
Каждый этаж автоматически сохраняет подробный текстовый лог в `logs/`.

## Запуск

Сундуки: `dotnet run -- --chests 5` создаёт до пяти сундуков на этаж,
по умолчанию — три; `--chests 0` отключает их. В API это `SpawnSettings.Chests`.
Сундук занимает один тайл, обозначается золотым `C` и получает один из четырёх спрайтов `object.chest.n`, `.e`, `.s`, `.w`
поверх пола коридора. Приоритет — тупики, затем свободные места у стен коридоров.
В тупике сундук стоит строго по центру торцевой стены напротив единственного прохода
и смотрит в сторону этого прохода. У обычной стены спинка обращена к стене, лицо — к полу.
Поле тайла `facing` в JSON задаёт направление лица: `n` вверх, `e` вправо,
`s` вниз, `w` влево (ось Y направлена вниз). Каждый спрайт имеет свой цвет на карте вариантов.
У обычной стены также выбирается центр стороны секции, а не угол.
Первое место выбирается случайно с предпочтением тупиков, следующие — по максимальному
расстоянию до ближайшего установленного сундука (тупики получают бонус к оценке 1.5).
Минимальное расстояние по прямой в тайлах: `max(9, min(tileWidth, tileHeight) / 4)`
с целочисленным делением; на стандартном этаже — 14 тайлов. Это ограничение
не ослабляется при большом запросе: если свободных мест недостаточно, сундуков будет меньше.
В JSON и конце JSONL значение записывается как `chestMinimumDistance`.
Стартовая комната, секция выхода и основной маршрут исключены. Если мест мало,
создаётся меньше сундуков, а консоль сообщает фактическое количество.
Сундуки пока проходимы (взаимодействие и содержимое ещё не реализованы).
Сундуки и враги находятся в отдельном слое `spawns`, а тайлы сохраняют тип пола.
У сундука есть `position`, `facing` и `spriteId`. На карте спавна `C` занимает один тайл.

## Спавн врагов и предметов

`DungeonGenerator` строит только этаж. После завершения отдельный `SpawnPlanner`
планирует сундуки и врагов, не изменяя геометрию и не расходуя случайные числа
строительства. Спавн привязан к общему seed этажа: одинаковые seed и настройки
дают одинаковые карту, сундуки и врагов. Отдельного seed спавна нет.
В конце выводится третья, отдельная тайловая карта спавна:
цветные `1`, `2`, `3`, `4` соответствуют ID `001`, `002`, `003`, `004`, `C` — сундук.
Это точки появления; поведение врагов, бой и содержимое сундуков не реализованы.

По умолчанию комнаты 4×3 получают одну пачку, 5×3 — две, 5×5 — три.
В комнатной пачке 5–6 врагов, в коридорной 2–4; на этаж запрашиваются шесть
коридорных пачек и три одиночных врага. В пачке могут быть разные типы.
Каждая пачка связна по соседним тайлам и не пересекает стены. Враги не занимают
тайлы сундуков и друг друга. Стартовая комната всегда безопасна; дополнительно
исключены тайлы в радиусе 15 от входа как по прямой, так и по пути по полу.
Секция выхода также исключена. Если ограничения мешают разместить полную пачку,
она пропускается, а причина записывается в `notes` и выводится в консоли.

Все настройки находятся в `spawn-settings.json`. Из `TestingUtil`:

```powershell
dotnet run --project .\ProceduralGeneration -- --seed 42 --spawn-config .\ProceduralGeneration\spawn-settings.json
```

| Поле JSON | По умолчанию | Значение |
| --- | --- | --- |
| `chests` / `chestDistance` | 3 / null | Число сундуков и дистанция в тайлах; null — автоматическая |
| `safeRadius` | 15 | Безопасная зона у входа в тайлах |
| `roomMin` / `roomMax` | 5 / 6 | Размер комнатной пачки |
| `corridorMin` / `corridorMax` | 2 / 4 | Размер коридорной пачки |
| `roomPacks` | 1 | Пачки в обычной комнате |
| `largeRoomPacks` / `largestRoomPacks` | 2 / 3 | Пачки в больших комнатах |
| `largeRoomArea` / `largestRoomArea` | 15 / 25 | Пороги площади комнат в секциях |
| `corridorPacks` | 6 | Количество пачек коридоров на этаж |
| `singles` | 3 | Количество одиночных врагов коридоров |
| `packRadius` | 5 | Максимальное расстояние от центра пачки по полу, в тайлах |
| `packDistance` | 9 | Минимальное расстояние между центрами пачек по прямой |
| `weight001` … `weight004` | 1 каждый | Относительные частоты типов; 0 исключает тип |

Все четыре веса равны нулю — врагов нет. Число пачек или одиночных врагов 0
отключает соответствующий вид размещения. Неуказанные поля берутся по умолчанию,
неизвестные поля и некорректные значения вызывают ошибку. Аргументы применяются
слева направо: `--spawn-config` загружает настройки, следующие `--chests`,
`--safe-radius`, `--corridor-packs`, `--singles` переопределяют их.
При нескольких этажах общий seed увеличивается на номер этажа минус один.

JSON карты версии 2 содержит отдельный объект `spawns` с настройками, seed,
массивами `chests` и `enemies`, замечаниями `notes`. У врага: `position`,
`enemyId`, `groupId`, `location` (`room`, `corridor`, `single`), `roomId`.
В JSONL этому соответствует отдельная запись `record: "spawns"`.
Чтение `tiles` восстанавливает этаж, чтение `spawns` — объекты на нём.

```csharp
SpawnPlan spawns = new SpawnPlanner(floor, new SpawnSettings { Chests = 3, CorridorPacks = 6 }, floorSeed: 42).Generate();
// Передавайте тот же seed, с которым построен floor.
```

В PowerShell / Windows Terminal:

```powershell
cd C:\Coding\games\Coinbound\TestingUtil\ProceduralGeneration
dotnet run
```

.NET SDK 10 уже установлен на текущем компьютере.
По умолчанию карта имеет размер **39×19 секций**, включая внешние стены.
Каждая секция содержит **3×3 = 9 тайлов**: полная карта имеет размер **117×57 тайлов**.
Один символ показывает один тайл. Обычно после символа идёт пробел; в узком
окне пробел убирается. Для полной анимации нужны **235 столбцов × 66 строк**,
либо **118 столбцов × 66 строк** без пробелов между тайлами.

Для компактного обзора, где символ обозначает целую секцию, запустите
`dotnet run -- --sections`. Для него достаточно окна **80 столбцов × 28 строк**.
Оба масштаба отображают одну и ту же карту и процесс её генерации.

**Пробел** — пауза/продолжение, **Q / Esc / Ctrl+C** — остановка.
Итоговая карта остаётся в терминале. Повторный запуск создаёт новый этаж.
Под обычной картой печатаются карта вариантов текстур, легенда и полный путь к логу.

По умолчанию между кадрами есть небольшая задержка **20 мс**, а новая подпись
остаётся видимой минимум **100 мс**. Кадры показываются по мере продвижения
прогресса: внутренние шаги объединяются, поэтому большая карта не получает
задержку после каждой секции или тайла. `--delay 0` отключает искусственное ожидание.
Процент отражает выполненные этапы и работу внутри них, а не оставшееся время.

В маленьком окне, при перенаправлении вывода и с `--plain` показываются цветные
снимки при смене подписи, продвижении минимум на 10% и в конце генерации.
Файловый вывод содержит ANSI-коды цвета; смотреть его нужно в совместимом
терминале, а не как обычный текст. При перенаправлении нет задержек и ожидания ввода.

## Комнаты, стены и фонтаны

Размер комнаты — **внутренний пол в секциях**, ширина по горизонтали × высота по вертикали.
Снаружи идёт стена толщиной в одну секцию (3 тайла). Внешняя граница всего этажа тоже
остаётся сплошной стеной. В стенах комнат есть открытые проходы из обычного
пола, без дверей и отдельного цвета. Остальная часть периметра остаётся стеной.

На экране `#` рисуется только рядом с полом: в тайловом режиме остаётся обводка
толщиной один тайл, включая диагональные углы. Остальная толща стен отображается
пробелами. В обзоре `--sections` то же правило применяется к соседним секциям.
Обводка появляется по мере прокладки пола во время генерации. Пробелы остаются
непроходимыми стенами в данных карты.

| Комната | Размер в секциях | Размер в тайлах | Объекты | Количество |
| --- | --- | --- | --- | --- |
| Стартовая | 3×4 | 9×12 | Вход в секции (2,2), фонтан в секции (2,3) | Всегда одна |
| Обычная | 5×5, 4×3 или 5×3 | 15×15, 12×9 или 15×9 | Свободный пол | Остальные комнаты |

Координаты секций внутри комнаты считаются **от 1**, от левого верхнего угла:
первая координата — столбец, вторая — строка. Вход, фонтан и выход занимают
по одному тайлу в центре своей секции; остальные восемь тайлов остаются полом.
В стартовой комнате вход находится в локальном тайле (5,5), фонтан — в (5,8),
если считать тайлы комнаты от 1. Стартовая комната расположена в левом верхнем
углу этажа. Фонтан пока проходим; игровое взаимодействие с ним в прототип не входит.
Коридор и открытый проход шириной в одну секцию имеют ширину 3 тайла.

У стартовой комнаты один открытый проход; у обычных —
по два на разных сторонах. Все комнаты и тайлы пола готового этажа доступны
из входа. Выход выбирается в **последней секции наиболее удалённого тупика**:
у неё ровно одна соседняя проходимая секция, остальные три — стены.
Дальность определяется длиной кратчайшего пути по секциям от входа.

Параметр `--rooms N` считает **только обычные комнаты** размером 5×5, 4×3 или 5×3 секции.
Стартовая 3×4 обязательна, добавляется сверх этого числа и не расходует лимит.
Например, `--rooms 4` — четыре обычные комнаты и стартовая, всего пять,
если для обычных комнат хватает места.

По умолчанию генератор пытается разместить **3–5 обычных комнат**. При недостатке
места обычных комнат будет меньше, но стартовая всегда сохраняется.
С `--rooms 0` остаются только стартовая комната и лабиринт.
На каждом этаже ровно один фонтан: в стартовой комнате, в центре секции (2,3).

## Цветные символы

| Символ | Цвет | Значение |
| --- | --- | --- |
| `#` | Серо-синий | Стена рядом с полом коридора или комнаты, включая углы |
| Пробел | Фон карты | Скрытая часть стены, не соседствующая с полом |
| `.` | Светло-серый | Пол коридора и открытого прохода |
| `.` | Песочный | Пол комнаты |
| `S` | Зелёный | Вход |
| `F` | Голубой | Фонтан |
| `E` | Красный | Выход в конечной секции тупика |
| `@` | Жёлтый | Текущий шаг генерации |
| `*` | Фиолетовый | Путь, если задан `--show-path` |

Легенда с цветными символами отображается под картой.
Вход, выход и фонтаны сохраняют свои цвета даже при подсветке пути.
Путь выбирается кратчайшим по секциям, затем соединяет их центры соседними
тайлами. Это путь по центру коридоров, без срезания углов внутри секций.

## Примеры

```powershell
# Четыре обычные комнаты плюс стартовая с фонтаном
dotnet run -- --seed 42 --rooms 4

# Компактная анимация: символ показывает секцию из девяти тайлов
dotnet run -- --sections

# Медленная генерация и подсветка пути
dotnet run -- --seed 42 --delay 60 --show-path

# Большая карта — увеличьте окно терминала
dotnet run -- --width 61 --height 25 --rooms 8

# Стартовая комната с фонтаном и лабиринт, без обычных комнат
dotnet run -- --rooms 0 --loops 0

# Пять этажей с seed 100, 101, 102, 103, 104
dotnet run -- --seed 100 --floors 5

# Быстрые цветные снимки процесса без перерисовки
dotnet run -- --seed 42 --plain --delay 0

# Проверки и справка
dotnet run -- --self-test
dotnet run -- --help
```

Прежний параметр `--halls N` сохранён как синоним `--rooms N`.

## Лог каждой генерации

Запуск автоматически создаёт отдельный файл для каждого этажа в
`C:\Coding\games\Coinbound\TestingUtil\ProceduralGeneration\logs`.
Имя содержит дату UTC, номер этажа, seed и уникальный идентификатор. Повторный
запуск с тем же seed создаёт новый файл. При запуске опубликованного приложения
вне проекта папка `logs` создаётся рядом с исполняемым файлом.

Формат — **UTF-8 JSON Lines (`.jsonl`)**, одна JSON-запись на строку, без рисунков
карты и ANSI-кодов. Его можно читать текстовым редактором или разбирать построчно.
Текущая версия формата — **2**: спрайт стены выбирается по её форме с исключением
избыточных диагоналей. Старые логи версии 1 сохраняют прежние ключи по полной маске.

| `record` | Содержимое |
| --- | --- |
| `header` | Версия формата, параметры генерации, seed, размеры, правила координат и масок |
| `step` | Каждый шаг генератора, стадия, процент, подпись и координаты секции |
| `room` | Номер комнаты, тип, границы в секциях и тайлах, открытые проходы |
| `sprite` | Ключ варианта, описание, цвет диагностики и поворот |
| `tile` | Спецификация одного тайла, включая скрытые стены и внешнюю границу |
| `end` | Статус, количества, вход/выход и маршруты в секциях и тайлах |

На карте по умолчанию будет ровно **6669 записей `tile`**: 117 × 57.
Координаты записываются построчно: сначала X=0..116 при Y=0, затем следующая строка.
В конце успешной генерации статус — `complete`; при Q / Esc / Ctrl+C — `cancelled`.
Если генерация прервалась иначе, лог по возможности завершается статусом `interrupted`.
В двух последних случаях записывается вся текущая, ещё незавершённая карта.
`--self-test` и `--help` пользовательские файлы логов не создают.

## Спецификация спрайтов

После успешной генерации каждого этажа рядом с `.jsonl` в папке `logs` сохраняется
отдельный **`.json` с тем же именем**. Это один обычный JSON-документ в UTF-8
с отступами, готовый для чтения целиком. Путь выводится в консоли как `JSON карты:`.
При отмене остаётся только лог незавершённой генерации; готовая карта не экспортируется.

В документе есть версия формата, номер этажа, seed и настройки, размеры секций
и тайлов, правила координат и выбора спрайтов, комнаты с проходами, каталог
используемых спрайтов, вход, выход, статистика и маршруты.
Массив `tiles` содержит **каждый тайл**, включая скрытые стены и внешнюю границу.
Его индекс — `y * dimensions.tileWidth + x`. Размер секции — 3×3 тайла.
Все атрибуты тайла описаны ниже; `kind` записывается строкой:
`wall`, `corridor`, `roomFloor`, `entrance`, `fountain` или `exit`.
Для загрузки карты достаточно `.json`; читать журнал шагов `.jsonl` не требуется.

Для каждого тайла записываются `x`, `y`, родительская `section`, локальный тайл
`localTile` (0..2), тип `kind`, проходимость `walkable`, видимость `visible`,
маска соседнего пола `floorNeighborMask`, нижний слой `terrainSprite`, объект
`objectSprite` и итоговый ключ для диагностики `spriteId`.
Для стены также записывается `wallSpriteMask` — маска формы, определяющая её спрайт.
У скрытой стены она равна 0, у пола и объектов — `null`.

Ключи — имена будущих спрайтов: реальные изображения и координаты в атласе пока
не задаются. При подключении графики нужно сопоставить каждому используемому
ключу изображение. Все варианты ориентированы явно, `rotationDegrees = 0`.

| Ключ | Какой спрайт использовать |
| --- | --- |
| `floor.corridor.0` / `.1` / `.2` | Три взаимозаменяемые текстуры пола коридора |
| `floor.room.0` / `.1` / `.2` | Три взаимозаменяемые текстуры пола комнаты |
| `wall.04` | Пол снизу: S, S+SE, S+SW и S+SE+SW используют один спрайт |
| `wall.01` | Пол сверху: N с любым сочетанием NE и NW |
| `wall.02` | Пол справа: E с любым сочетанием NE и SE |
| `wall.08` | Пол слева: W с любым сочетанием NW и SW |
| `wall.20` / `.40` / `.10` / `.80` | Внешние углы: пол только по диагонали SE / SW / NE / NW |
| `wall.09` | Пол N+W; наличие NE, SW и NW не меняет спрайт |
| `wall.06` | Пол S+E; наличие NE, SE и SW не меняет спрайт |
| `wall.14` | Пол S+NE: отдельный угол NE сохраняется, SE и SW не влияют |
| `wall.XX` | Остальные формы: XX — упрощённая маска `wallSpriteMask` в hex |
| `object.entrance` / `object.fountain` / `object.exit` | Единственный объект поверх соответствующего пола |
| `none` | Не рисовать спрайт: скрытая стена остаётся непроходимой |

Маска смотрит **из текущего тайла на соседний пол**: N=1, E=2, S=4, W=8,
NE=16, SE=32, SW=64, NW=128. X растёт вправо, Y — вниз.
`floorNeighborMask` всегда сохраняет **всех реальных соседей**, без упрощения.
Например, для S+SE+SW она равна 100 = 4 + 32 + 64, но `wallSpriteMask = 4`,
а ключ спрайта — `wall.04`.

**Диагональ влияет на текстуру только тогда, когда пол отсутствует с обеих
прилегающих прямых сторон.** Угол NE учитывается без N и E, SE — без S и E,
SW — без S и W, NW — без N и W. Поэтому S и S+SE имеют один спрайт, а только SE
и S+NE сохраняют самостоятельные формы. Пол находится на соседних тайлах;
спрайт стены описывает только саму стену.

Всего из 256 сочетаний соседей получается **46 видимых форм стен** и `none`
для стены без соседнего пола. В каталоге и легенде нет вариантов для избыточных
масок. Одинаковая форма всегда получает одинаковый ключ и цвет.

Вариант пола выбирается из seed, координат тайла и материала. Он повторяется
при повторном запуске и не влияет на геометрию или случайные числа генератора.
Вход, фонтан и выход имеют **два слоя**: обычный пол снизу и один объект сверху.

Вторая карта всегда показывает **каждый тайл**, даже при `--sections`.
Символы и пробелы совпадают с обычной тайловой картой; подсветка пути в неё не
переносится. Цвет указывает `spriteId`: для объекта это его верхний слой,
для остальных тайлов — `terrainSprite`. Цвет закреплён за ключом и одинаков
между этажами. Под картой есть легенда с ключом, цветом и описанием каждого
показанного варианта; точное назначение любого тайла можно прочитать в логе.

Получить те же данные в C# после завершения генерации:

```csharp
TileSpriteMap sprites = TileSpriteMap.Create(generator.Map, seed: 42);
TileSpecification spec = sprites.Get(new TilePosition(7, 10));
// spec.TerrainSprite: floor.room.0, .1 или .2
// spec.ObjectSprite: object.fountain
// spec.SpriteId: object.fountain — ключ цвета во второй карте
SpriteVariant variant = TileSprites.Variant(spec.SpriteId);
// variant.Description, variant.DebugColor, variant.RotationDegrees

int wallMask = TileSprites.WallSpriteMask((int)(FloorNeighbors.S | FloorNeighbors.SE));
// wallMask == 4: тот же wall.04, что и для S или S+SE+SW.
// У стены spec.FloorNeighborMask хранит полную маску, spec.WallSpriteMask — упрощённую.
```

## Алгоритм

1. Заполнить план секций и тайловую сетку стенами. Спланировать комнаты с точными размерами, их
   внутренний пол, стену по периметру и открытые проходы. Между стенами
   соседних комнат оставить место для коридоров. У границы зарезервировать
   короткую тупиковую ветку, защищённую от добавления обходных путей.
2. Постепенно построить комнаты, установить вход и фонтан в стартовой комнате.
   Их периметры зарезервированы и защищены от дальнейшего прорубания.
3. Итеративным DFS с возвратом проложить лабиринт шириной в одну секцию на свободной
   сетке. При обходе комнат могут появляться отдельные участки.
4. Провести коридор от каждого открытого прохода до лабиринта, затем объединить все
   участки поиском кратчайших соединений. Защищённые стены не пересекать.
   Убрать диагональные касания: в любом блоке 2×2 секции запрещено чередование двух
   секций пола и двух стен по диагонали. Такие стыки соединяются через соседнюю
   секцию; стены комнат и защищённая тупиковая ветка сохраняются. После изменения
   повторно проверяются соседние блоки, чтобы исправление не создавало новый стык.
5. Добавить случайные обходные проходы с вероятностью `--loops`.
6. Среди конечных секций тупиков выбрать самую удалённую от входа и разместить
   выход. Защищённая ветка гарантирует наличие тупика даже при `--loops 1`.
   Поиском в ширину восстановить кратчайший путь по секциям от фиксированного входа.

При изменении секции сразу обновляются все её девять тайлов. Тайловая сетка
существует на каждом шаге генерации и доступна независимо от способа отображения.

Во время строительства отдельные комнаты и участки ещё могут быть изолированы.
После стадии соединения весь пол связан. Внешняя стена и стены комнат
сохраняются на всех стадиях.

Одинаковые параметры и seed в этой версии приложения/.NET дают одинаковый
этаж независимо от скорости и отображения. Этажи генерируются отдельно.

## Настройки

| Параметр | По умолчанию | Значения |
| --- | --- | --- |
| `--width` | 39 | Нечётное число секций 11–151 |
| `--height` | 19 | Нечётное число секций 11–81 |
| `--seed` | Случайный | 32-битное целое |
| `--floors` | 1 | 1–100 |
| `--rooms` / `--halls` | 3–5 | 0–8 обычных комнат; стартовая сверх лимита |
| `--loops` | 0.08 | 0–1, дробная часть через точку |
| `--delay` | 20 мс | 0–1000, между кадрами; 0 отключает задержки |
| `--sections` | Выключен | Обзор секций вместо подробной тайловой сетки |

## Использование в игре

`DungeonGenerator` и `DungeonMap` не зависят от консоли:

```csharp
var generator = new DungeonGenerator(new GenerationSettings(Seed: 42, HallCount: 4));
foreach (GenerationStep step in generator.Generate())
{
    // generator.Map уже обновлена: здесь можно перерисовать собственный экран.
    // step.Progress — 0..100, step.Status — подпись этапа для экрана загрузки.
}
DungeonMap floor = generator.Map;
Cell section = new(2, 3); // Координаты секции, от нуля
TileKind sectionKind = floor.GetSection(section); // Fountain
TilePosition position = floor.SectionCenter(section); // (7,10), отдельный тайл
TileKind tile = floor.GetTile(position); // Единственный Fountain
bool canWalk = floor.IsTileFloor(new TilePosition(6, 9)); // Обычный пол рядом
Cell parentSection = floor.SectionAt(position); // (2,3)
IReadOnlyList<DungeonRoom> rooms = floor.Rooms;
IReadOnlyList<TilePosition> tilePath = floor.TileSolution;
```

Координаты самой карты в API считаются от нуля. `Cell`, `Width`, `Height`,
`FloorCount`, `Entrance`, `Exit`, `Solution`, `IsFloor`, `Floors` и `Neighbors`
относятся к секциям. `TilePosition`, `TileWidth`, `TileHeight`, `FloorTileCount`,
`EntranceTile`, `ExitTile`, `TileSolution`, `GetTile` и `IsTileFloor` — к тайлам.
`SectionOrigin` возвращает верхний левый тайл секции, `SectionCenter` — центральный.
У комнаты есть отдельные `TileLeft`, `TileTop`, `TileWidth`, `TileHeight`.
Параметр `HallCount` в API,
как и `--rooms`, ограничивает только обычные комнаты. Генератор одноразовый:
для следующего этажа создавайте новый экземпляр. Для хранения промежуточных
снимков копируйте клетки: текущая карта меняется после каждого шага.

`--self-test` проверяет точные размеры и объекты комнат, ограничение фонтанов,
сплошные стены, открытые проходы, отсутствие диагональных стыков, выход строго в тупике, связность, кратчайший путь,
повторяемость, промежуточные состояния, монотонный прогресс 0–100%,
подписи этапов, развёртку секций в 3×3 тайла на каждом шаге, одиночные объекты,
непрерывность тайлового пути, оба масштаба отображения и ошибочные аргументы.
Также проверяются все 256 масок соседей и их объединение в формы стен, слои спрайтов, повторяемость вариантов
пола, уникальность цветов, полное описание карты в JSONL и сохранение отменённой генерации.
