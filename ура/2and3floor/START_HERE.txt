decorations/manifest.json — основной источник данных для всех80 новых PNG. Пути file относительны к decorations/. Каждый объект имеет ID, подпись, размер, pivot, коллизии, правила стен, слой и разрушение. Дополнительно есть отдельные manifest.json для forge/crypt/plants.
Отдельные PNG можно разместить в самостоятельных папках Resources/DungeonDecorForge, DungeonDecorCrypt и DungeonPlantsCrypt, сохранив .meta. ID forge_XX, crypt_XX, plants_XX уникальны. Не смешивать их с таблицей wall-масок.
Альтернатива отдельным PNG — decorations/runtime_atlas_512.png с Rect из manifest.json. Это один лист512×512 с прозрачными промежутками2px, без поворотов и масштабирования. Multiple, PPU32, Point. Имена и индивидуальные pivot восстановить из manifest, а не назначать всем pivot в центре. Выбрать один способ импорта.
В runtime не создавать дополнительные материалы для каждого объекта. Использовать общий материал и атлас. Спрайты неподвижные; им не нужны Update и Animator на каждом кусте. Свечи в этом наборе статичные; встроенных циклов пламени и новых источников света нет.

РАЗМЕЩЕНИЕ У СТЕН — ВАЖНО
Все направления относятся к стене относительно предмета на полу: N — стена над ним, S — под ним, W — слева, E — справа. Координаты карты: X вправо, Y вниз. Использовать placement.walls_relative_to_floor_prop; reject_wrong_wall=true. Не искать случайное место в центре комнаты при отсутствии нужной стены.
Прижимать ВИДИМУЮ границу PNG к внутренней кромке стены с зазором0px. Не ориентироваться на прозрачный край холста и не придвигать к внешнему контуру текстуры стены.
Пусть visible_bbox_top_left=[l,t,r,b], а desiredX/desiredY — координаты внутренней границы стены в пикселях карты. Для N: originY=desiredY-t. Для S: originY=desiredY-b. Для W: originX=desiredX-l. Для E: originX=desiredX-r. По второй оси центрировать bbox. Для угла выполнить обе формулы. Перевести origin+pivot в мировые координаты с PPU32, инвертируя Y при переходе к Unity.
Горн, стойка, верстак, надгробие, саркофаг, гроб, молитвенники и основание статуи имеют ограничения N в manifest. Не разворачивать их к другой стене случайным flip/rotation.
УГЛЫ ПРОВЕРЕНЫ ПО ГОТОВОМУ РИСУНКУ: forge_12 ставится в SW, crypt_12 — в SE. plants_16 и plants_39 — NW, plants_40 — NE. Не определять угол по предположению или первоначальному промпту.
plants_25/26 — накладки для N, plants_27 — W, plants_28 — E, plants_29/30/31/32 — NW/NE/SW/SE. Это прозрачный плющ. Для прямой N-стены выбирать грань, у которой пол с юга(mask&4); для W — пол с востока(mask&2); для E — пол с запада(mask&8). Не путать стороны стены и стороны пола.
Накладку wall_overlay рисовать на соответствующей стене, а не как новый препятствующий тайл. Для углов проверять наличие обеих нужных стен. В составной группе слой родителя имеет приоритет над слоем отдельного растения.
Большие уголки plants_39/40 резервируют только клетки placement_cells: у NW-композиции свободен SE-квадрат, у NE-композиции свободен SW. Не заполнять эти свободные клетки большим прямоугольным коллайдером.

ХИТБОКСЫ, ВЕРХНЯЯ ЧАСТЬ И СОРТИРОВКА
Точные прямоугольники каждого объекта записаны в manifest и в PLACEMENT_AND_HITBOXES.csv. Они охватывают основание, а не всю картинку. Верх текстуры не получает коллизию: игрок может проходить за верхом предмета, а визуальная сортировка идёт по основанию.
rects_px_top_left используют X вправо,Y вниз, до вычитания pivot. rects_px_bottom_left уже переведены в Y вверх. Для BoxCollider2D: size=(w/32,h/32); offset=((x+w/2-pivotX)/32,(y+h/2-pivotY)/32) по bottom-left записи. Не переворачивать Y второй раз.
У каждой сборки список нескольких прямоугольников, соответствующих её частям. Пустой промежуток между предметами не блокировать объединяющим box. placement_cells нужны для резервирования места при спавне, они не являются физической коллизией.
Мох, листья, травы, цветы, корни и кусты в этом наборе не имеют коллизий, HP, случайного урона или замедления. Цепь, инструменты, кости и небольшие грибы также проходят как лёгкий декор. ground_detail находится ниже персонажа. feet_sorted сортируется по pivot у основания; wall_overlay следует порядку отрисовки стены.
Плотность начинать с небольших групп вдоль стен и редких пустых участков между ними. Центральные боевые проходы, выходы и места появления персонажей держать свободными. Не создавать новый куст на каждом тайле и не перекрывать дверной проём; зарезервировать минимум2 клетки около выхода. На макете склепа56 размещений, включая43 растения/группы/накладки.

ТОЧНЫЕ СБОРКИ И РАЗРУШЕНИЕ
16 сборок действительно составлены из исходных PNG целочисленным смещением и альфа-композицией. Не генерировать их заново и не перекрашивать отдельно. Рецепты перечисляют components с offset_px_top_left и порядком наложения.
Неразрушаемая сборка может рисоваться одним готовым PNG. Сборку с разрушаемой частью создавать из её компонентов: отдельные SpriteRenderer с общим материалом/атласом, коллайдеры оснований и HP только у разрушаемых частей. Не рисовать одновременно сборочный PNG и его компоненты.
При размещении дочернего элемента: childOriginBottomLeft=(offsetX,parentHeight-offsetY-childHeight). childLocalPosition=(childOriginBottomLeft+childPivot-parentPivot)/32. Это сохраняет положение пикселей исходного рецепта. При необходимости использовать SortingGroup родителя и порядок компонентов, чтобы перекрытия совпадали с PNG.
Удар адресовать поражённому компоненту. HP берётся из hp_base_melee_multiplier, умноженного на базовый урон ближней атаки в начале забега, не на текущий усиленный урон. Камень и железные основания остаются целыми; дерево, меха, урны и корзина могут разрушаться согласно manifest.
При летальном ударе один раз: пометить компонент разрушенным; немедленно выключить его Collider2D и приём урона; убрать его SpriteRenderer; выпустить ограниченный пакет частиц; положить указанные общие обломки и оставшиеся предметы. Другие компоненты сборки сохраняются. Повторный удар по уже уничтоженной части ничего не создаёт.
У стойки/верстака после разрушения остаются инструменты forge_14; у гроба — кости crypt_08. Корзина даёт только лёгкие частицы листьев без постоянного спрайта обломков. Списки debris_ids и survivor_ids заданы для каждого базового объекта. Автоматический лут выключен.
Обломки — всего4 общие текстуры: forge_15 древесина, forge_16 уголь/металл, crypt_15 черепки, crypt_16 гнилые доски. Они без коллизий и HP, рисуются у основания ниже персонажа. Не создавать уникальную текстуру для каждого разрушенного предмета.
Состояние хранить по roomId+placementId+componentIndex. После повторного входа в комнату уничтоженные части не возрождаются. У целых частей сохраняется прежнее состояние.

ЧАСТИЦЫ И ЛИМИТЫ
decorations/particle_profiles.json задаёт8 лёгких профилей. Обычно6–10 частиц по1–2px, короткие дуги0.2–0.45с. Дерево — тёмные щепки, уголь — почти чёрные крошки, металл — редкие серые точки без свечения, керамика — небольшие черепки, кадка — несколько тёмных капель, корзина — сухие листья.
Использовать общий пул, максимум96 одновременно активных частиц и не более12 на одно событие. Без Rigidbody/Collider на частицах, теней, дыма высокого разрешения, bloom и динамического света. Обновлять одним общим менеджером. Обломки складывать в общий статичный слой, ограничить примерно24 наборами на комнату, удаляя старые или объединяя в слой по принятой в проекте логике.
Это разумные начальные ограничения, а не измеренный FPS. Обязательно проверить импорт, свет, читаемость персонажей и производительность на целевом устройстве. Текущий архив содержит арт и спецификацию, не готовое изменение кода игры.
